# Workspaces and local analysis tools

## Scope and workspace selection

This guide applies to any supported Unity Android game. It defines tool roles,
installation layout and operating rules; it does not select a game, package ID,
capture date, device or workstation for the agent.

1. Start from the package ID or existing workspace supplied by the user. When
   acquisition is requested, use ADB to inspect installed packages and collect
   authorized APK splits, OBB and accessible content. Report package mismatches
   explicitly; never silently substitute another application.
2. Inspect acquisition/pipeline manifests and the package/version identity of
   each candidate workspace. Check stage status and artifact presence. A recent
   directory name alone does not establish a complete or compatible capture.
3. Choose one working workspace for the acquired build. Start with
   `blueprint/index.html`, `blueprint/overview.md`, `blueprint/report.json` and
   `extracted-assets/game_model.json` when present. Missing or failed stages must
   be completed before treating their outputs as usable evidence.
4. Keep per-game folder inventories, chosen workspace paths, source hashes,
   capture versions and analysis results inside that game's workspace. Consult
   any supplementary execution/source-coverage reports if provided, but do not
   assume custom reports are standard CLI outputs.
5. Reuse existing inputs for follow-up analysis. Each producing command requires
   a new or empty output directory within the workspace. Preserve earlier output
   and record which verified output is current in the workspace's local notes.
   A fresh `uare run` requires a new workspace; it does not resume a populated
   workspace. Use individual stage commands to retry failed stages.

Preserve references to raw acquisition folders when consolidating evidence.
Different builds or cached-content versions must retain their provenance; do not
merge them solely because they share a game name. Pipeline completion establishes
artifact generation, not Unity import, compilation or gameplay correctness.

## Tool roles and layout

| Tool | Local path | When it is needed | Output / limitation |
| --- | --- | --- | --- |
| ADB | `vendor/platform-tools/<platform>/` | Acquire installed APK splits and accessible device content | Acquisition only; does not decode Unity objects |
| UnityPy and power dependencies | Project Python environment, declared in `pyproject.toml` | Read scenes, prefabs, hierarchy, assets and serialized animation data | Keep Python environments in place; moving a venv breaks absolute launch paths |
| ILSpy | `vendor/ilspy/ilspycmd` | Decompile genuine managed DLLs, including recovered HybridCLR hot-update code | Readable C#; not original comments, layout or a verified compiling game |
| Il2CppDumper | `vendor/il2cpp-dumper/Il2CppDumper` | Join `libil2cpp.so` with matching metadata to recover types, signatures and RVAs | `dump.cs` and DummyDll are structural stubs, not recovered method bodies |
| Ghidra | `vendor/ghidra/analyzeHeadless`, distribution in `vendor/ghidra/app/` | Analyze native logic that managed code cannot explain | Function listing and pseudo-C, requiring interpretation and address validation |
| Compatible JDK | `vendor/jdk21/Contents/Home/` (macOS) or `vendor/jdk21/` (Linux) | Run the installed Ghidra and compile Java analysis scripts | Host dependency only; not a game SDK or a requirement for asset extraction |

Check the actual installed versions and host architecture before execution.
Native launchers, JDKs and Ghidra native components must match the host OS/CPU.
The tracked shell launchers target POSIX hosts; on Windows use compatible native
entry points through the CLI's explicit tool arguments or environment variables.
Do not infer installed tools from the existence of this guide or a launcher.

Reusable distributions belong under `vendor/`. Downloads, runtime caches,
virtual environments and one-off game scripts are not interchangeable with those
installations. Do not relocate virtual environments or promote legacy scripts
without checking their dependencies and input contracts. The supported Ghidra
export script is generated by `src/uare/ghidra.py`.

## Resolution and runtimes

The CLI resolves an explicit tool argument first, then `UARE_IL2CPP_DUMPER`,
`UARE_GHIDRA` or `UARE_ILSPY`, then its corresponding `vendor` directory, then
PATH. An invalid explicit override fails instead of silently falling back.

- The Ghidra launcher respects `JAVA_HOME`; otherwise it uses
  `vendor/jdk21/Contents/Home` (macOS) or `vendor/jdk21` (Linux layout).
  It validates `java` and `javac`, prepends their directory to PATH and disables
  interactive input. Check the distribution's `Ghidra/application.properties` for its JDK requirement.
- Il2CppDumper runs its DLL through `dotnet --roll-forward Major`. This allows
  a net6 payload to use a compatible installed newer major runtime; verify the
  selected combination with an actual export. Keep
  `RequireAnyKey` set to `false` in its local `config.json`. The wrapper disables
  stdin; missing tools or incompatible runtimes must fail, not prompt.
- Inspect the managed tool's `*.runtimeconfig.json` and `dotnet --list-runtimes`
  to determine runtime compatibility. For example, ILSpy 11.1.0.9782 targets
  .NET 10; other versions may differ. The launchers do not install .NET. Supply
  a compatible runtime before running managed tools.
- Ghidra exports use a Java post-script, so Jython is unnecessary. The adapter
  checks the script's completion marker because a headless process can exit zero
  even when a post-script fails. Failed export must not become a successful stage.

## Commands for agents

Run from the repository root. Use an absolute interpreter path if selecting an
existing environment, because tests also invoke wrappers from other directories.
The commands below assume a configured `.venv-power`; substitute the actual
interpreter if needed. Replace the input paths with paths verified from the
selected capture. Choose an ABI present in that capture and matching metadata.

```bash
export UARE_PYTHON="$PWD/.venv-power/bin/python"
UARE_WORKDIR="/absolute/path/to/selected-workspace"
UARE_NATIVE_LIBRARY="/absolute/path/to/matching/libil2cpp.so"
scripts/uare doctor
dotnet --list-runtimes
vendor/ilspy/ilspycmd --version
# macOS vendored layout; use "$JAVA_HOME/bin/java" for an explicit JDK.
vendor/jdk21/Contents/Home/bin/java -version

# Optional native enrichment, only into a new/empty output directory.
scripts/uare il2cpp-enrich "$UARE_WORKDIR/extracted" \
  --so "$UARE_NATIVE_LIBRARY" --out "$UARE_WORKDIR/enriched-review"

# The vendored launcher selects the local JDK automatically.
scripts/uare decompile "$UARE_NATIVE_LIBRARY" \
  --out "$UARE_WORKDIR/native-review"

scripts/run-tests -p 'test_ghidra.py'
scripts/run-tests -p 'test_il2cpp_tools.py'
scripts/run-tests -p 'test_mono_decompile.py'
```

Do not run full native decompilation just to check installation. Use a small
known native binary for an actual export smoke test and keep results under
`re/tool-verification-*`. A tool's version output only proves it starts.

## Provisioning another checkout

Large optional payloads are Git-ignored. A clone includes launchers and guides,
not these local installations. Preserve upstream license files in each payload.
Use a trusted, pinned release archive and verify its SHA-256 before extraction.
Do not infer a trusted download URL or checksum from a filename.

1. Extract the Ghidra distribution into `vendor/ghidra/app/`, leaving the tracked
   launcher at `vendor/ghidra/analyzeHeadless` intact.
2. Extract a host-compatible JDK under `vendor/jdk21/`, or set `JAVA_HOME` to
   an existing compatible installation.
3. Extract the Il2CppDumper net6 payload directly into `vendor/il2cpp-dumper/`,
   alongside the tracked launcher, and disable `RequireAnyKey`.
4. Select a pinned ILSpy release compatible with the host runtime. For example,
   with a .NET 10 SDK/runtime available, install this release locally:
   `dotnet tool install ilspycmd --version 11.1.0.9782 --tool-path vendor/ilspy`.
5. Run resolver tests and an actual small export before using the tools on a
   game. Record version, platform, source archive/hash and verification result.

If a Ghidra archive lacks a native decompiler for the host, build the missing
component using the distribution's instructions and available compiler. The
following recipe was verified with Ghidra 12.1.4 on macOS ARM64 and requires
Xcode command-line tools. Check source/build compatibility before using it with
a different release; run from the repo root:

```bash
make -C vendor/ghidra/app/Ghidra/Features/Decompiler/src/decompile/cpp \
  -j4 ghidra_opt 'ARCH_TYPE=-arch arm64' \
  'ADDITIONAL_FLAGS=-mmacosx-version-min=11.0'
mkdir -p vendor/ghidra/app/Ghidra/Features/Decompiler/os/mac_arm_64
cp -n vendor/ghidra/app/Ghidra/Features/Decompiler/src/decompile/cpp/ghidra_opt \
  vendor/ghidra/app/Ghidra/Features/Decompiler/os/mac_arm_64/decompile
```

This builds the decompiler component only. For other native features/platforms,
follow the distribution's `vendor/ghidra/app/GettingStarted.md`, section
"Building Native Components". Do not claim all native features were verified.

Do not globally install tools, commit binary payloads, move virtual environments,
or remove caches/captures as an incidental part of analysis.
